# Chunked uploads for sessions over the 20 MB per-request cap

## Problem

`POST /api/chats` is a single-request endpoint capped at **20 MB** (`MAX_UPLOAD_BYTES`,
`server/src/api/headers.ts:4`, enforced by `bodyLimit` on every route). A real ZCode/Claude
Code session shaped into the upload payload can exceed that — and the user wants to be able
to publish arbitrarily large sessions. The requirement:

1. **Keep the per-request upload cap at 20 MB** (unchanged — `MAX_UPLOAD_BYTES` stays as is).
2. **If a session is larger than 20 MB, chunk it** so it still publishes.
3. **A CLI flag (`--no-chunk`) overrides** the chunking behavior.

## Decisions (locked with the user)

- **One share across all chunks.** A large session is published as a *single* share whose
  messages are delivered in ordered chunks. The viewer shows the full transcript as one
  share — not N separate links.
- **`--no-chunk`** sends the full session as a single upload regardless of size. If it
  exceeds the server's 20 MB per-request cap, the server returns `413 too_large` and the CLI
  prints a clear error telling the user to drop the flag.

## Why chunk at the CLI (not the server)

`prepareContent` (`server/src/redact/prepare.ts`) is **byte-stable per message**: every
redaction rule (`server/src/redact/rules.ts`) is a pure per-string regex with no
cross-message state, and `prepareContent` maps messages independently. So redacting a
*subset* of a session's messages yields identical bytes to redacting the whole session, and
the per-category counts sum exactly across chunks. This means the **CLI can split a session
into ≤20 MB message-groups and send each as an independent request**, and the server needs
only to *append* a chunk to an existing share — no new in-memory upload state, no
transaction spanning requests, no change to the redaction pipeline.

Concretely:
- **First chunk** = `POST /api/chats` (existing endpoint, unchanged). The server redacts the
  chunk's messages, computes the share row, and inserts the chunk's messages with
  `chunk_seq = 0`. Response gains `uploadId` (the share `id`) + `chunkCount`.
- **Subsequent chunks** = `POST /api/chats/:token/chunks` (new). The server redacts the
  chunk's messages and appends them with `chunk_seq = n`, updating the share's
  `messageCount`/`bytes`/`redactions` atomically.
- **Viewer** merges chunks in `(chunk_seq, seq)` order — a one-line ordering change.

The per-request cap **stays at 20 MB** (`MAX_UPLOAD_BYTES` is untouched). Chunking exists
precisely *because* the cap is 20 MB: a session whose shaped payload exceeds 20 MB is split
into ≤20 MB message-groups, each of which fits under the existing cap. No server-side cap
change is needed.

## Changes

### 1. Server — cap unchanged (no change)
- `MAX_UPLOAD_BYTES` stays at `20 * 1024 * 1024` (`server/src/api/headers.ts:4`). The existing
  "413 too_large above 20 MB" test in `server/test/middleware.test.ts` is unchanged. Chunking
  is what lets a session exceed the 20 MB per-request cap, so the cap itself is not touched.

### 2. Server — schema + migration (append support)
- `server/src/db/schema.ts`
  - `shares`: add `uploadId: text('upload_id').notNull().unique()` (a 128-bit
    `crypto.randomBytes(16)` hex id, generated server-side on create — distinct from the
    viewer-facing `token` so the chunk endpoint is keyed on an opaque id, not the share URL).
  - `share_messages`: add `chunkSeq: integer('chunk_seq').notNull().default(0)` and widen the
    primary key to `(shareId, chunkSeq, seq)` so a chunk can re-send without colliding.
- `server/drizzle/0001_chunked_upload.sql` (generated by `drizzle-kit generate` from the
  schema diff) — `ALTER TABLE shares ADD COLUMN upload_id ... UNIQUE`,
  `ALTER TABLE share_messages ADD COLUMN chunk_seq integer NOT NULL DEFAULT 0`, drop +
  recreate the `share_messages` PK as `(share_id, chunk_seq, seq)`.
- Backfill: existing rows get `chunk_seq = 0` (the column default) and a generated
  `upload_id`. Because the live DB is currently empty of real shares (all test shares were
  revoked) and the migration runs at server start, the default handles existing rows; the
  migration sets a unique `upload_id` for any pre-existing `shares` rows via
  `gen_random_uuid()::text` if present.

### 3. Server — create returns uploadId; new append endpoint
- `server/src/api/owner.ts`
  - `POST /api/chats`: generate `uploadId` (`generateUploadId()`), insert it on the share
    row, insert chunk messages with `chunkSeq: 0`; response gains `uploadId` and
    `chunkCount: 1`.
  - `POST /api/chats/:token/chunks` (new, API-key auth via the existing `/api/chats/*`
    guard): body `{ uploadId, chunkSeq, messages }` (zod: `uploadId` string, `chunkSeq`
    non-neg int, `messages` = the existing `messageSchema` array). Look up the share by
    `token`; **verify `uploadId` matches** (mismatch → `400` — prevents appending to the
    wrong share). In a transaction: `prepareContent(chunk.messages, share.preset)`, insert
    the chunk's messages with the given `chunkSeq` (seq = 1..n within the chunk), and
    `UPDATE shares SET message_count = message_count + ?, bytes = bytes + ?, redactions =
    redactions || ?` (jsonb merge of the per-category counts). Return `{ ok: true,
    messageCount, bytes }`.
  - New schema in `server/src/api/schema.ts`: `chunkBodySchema`.
- `server/src/security/token.ts` — add `generateUploadId()` = `randomBytes(16).toString('hex')`
  (32 hex chars; hex, not base64url, so it never needs URL-encoding in the chunk body), next
  to `generateShareToken()`.

### 4. Server — viewer merges chunks
- `server/src/api/public.ts` — the public endpoint today orders by `seq` alone and uses a
  single-int cursor (`parseCursor`, `gt(shareMessages.seq, cursor)`, `nextCursor = last.seq`).
  Change it to order by `(chunk_seq, seq)` and make the cursor a `(chunkSeq, seq)` pair:
  encode as `chunkSeq:seq` (e.g. `1:42`), decode in `parseCursor`, and the "after cursor"
  predicate becomes `(chunk_seq > c) OR (chunk_seq = c AND seq > s)`. `nextCursor` is built
  from the last row's `(chunkSeq, seq)`. This is what lets lazy-loading page correctly
  *across* chunk boundaries (chunk 0's tail → chunk 1's head). The response `messages` array
  already carries `seq`; add `chunkSeq` so the client can order/track if needed.

### 5. CLI — chunking + `--no-chunk`
- `cli/src/chunk.ts` (new) — `chunkMessages(messages, maxBytes): ShapedMessage[][]`. Greedy
  packing: accumulate messages into the current chunk until adding the next would push the
  chunk's serialized size (`JSON.stringify` of the chunk's messages) over `maxBytes`, then
  start a new chunk. A single message larger than `maxBytes` gets its own chunk (it will
  fail server-side with 413 — acceptable; such a message is pathological). Returns ≥1 chunk.
  `maxBytes` is the **20 MB** per-request cap (a CLI-side constant mirroring
  `MAX_UPLOAD_BYTES`; the chunk target is slightly under it to leave room for the JSON
  envelope — e.g. 19 MB).
- `cli/src/api.ts` — add `createChunk(token, { uploadId, chunkSeq, messages })` →
  `POST /api/chats/:token/chunks`. `create()` response type gains `uploadId`.
- `cli/src/commands/publish.ts`
  - `PublishValues` gains `noChunk?: boolean`.
  - After the preview + confirm, compute the payload byte size. If `noChunk` is set, send
    the whole session via `create()` (single request) — on a `413`, print
    "session is N MB, over the 20 MB per-request cap; re-run without --no-chunk to chunk".
    Otherwise, if the session is ≤ 20 MB, send it as a single `create()` (the common path,
    unchanged behavior). If > 20 MB, `chunkMessages()` it, send chunk 0 via `create()`,
    then loop `createChunk()` for the rest, printing progress
    (`Uploading chunk 2/7 (12.3 MB)…`).
- `cli/src/index.ts` — add `noChunk: { type: 'boolean', default: false }` to the `publish`
  `parseArgs` options; update `USAGE` to document `--no-chunk`.

### 6. Tests
- **Server unit/integration** (`server/test/owner.api.test.ts`):
  - create returns `uploadId` + `chunkCount: 1`.
  - append a second chunk → `messageCount`/`bytes` accumulate, messages stored with
    `chunk_seq = 1`, redaction counts merge.
  - append with a **wrong `uploadId`** → 400.
  - append to an unknown token → 404.
  - a chunk whose messages contain a secret is redacted on append (server-side redaction
    holds for chunks too).
- **Server** (`server/test/public.api.test.ts`): a share with 2 chunks serves messages in
  `(chunk_seq, seq)` order across the cursor.
- **CLI unit** (`cli/test/chunk.test.ts`, new): `chunkMessages` packs to ≤ maxBytes, keeps
  order, handles a single oversized message, and a small session yields exactly 1 chunk.
- **CLI unit** (`cli/test/publish.test.ts`): with a `fakeApi` whose `create`/`createChunk`
  are spies, a session that "exceeds" the cap (inject a small cap) produces 1 `create` +
  N-1 `createChunk` calls in order; `--no-chunk` produces exactly 1 `create` and 0
  `createChunk`.
- **CLI process** (`cli/test/publish.test.ts`): the mock server gains a
  `/api/chats/:token/chunks` route; a fixture session large enough to chunk (or an injected
  small cap) drives the real CLI through `create` + `createChunk` and asserts the chunk
  requests were received in order.
- **E2E** (`e2e/test/share.spec.ts`, optional but recommended): create a share via two
  chunks (chunk 0 via `POST /api/chats`, chunk 1 via the new endpoint) and assert the
  viewer renders messages from both chunks in order.

## Out of scope
- No change to the per-request upload cap (stays 20 MB) or to the redaction rules/presets.
- No streaming/multipart upload protocol — chunking is at the *message* level, each chunk a
  normal JSON request under the 20 MB cap.
- No resume/retry of a partially-uploaded chunk (a failed chunk re-runs the whole publish;
  the share row is rolled back per-chunk on failure, so no orphan partial share is left
  visible — see below).

## Failure / atomicity notes
- Each chunk's insert + share-row update is in **one transaction**, so a failed chunk never
  leaves a half-written chunk. If chunk *k* fails after chunk *k-1* succeeded, the share
  exists with *k-1* chunks (a valid, smaller share) — the CLI reports which chunk failed and
  the user re-runs. (Full all-or-nothing across chunks would require server-side upload
  state; not worth it for v1.)
- The `uploadId` check on append is the guard against appending to the wrong share; the
  `token` in the URL is the share's public id, `uploadId` is the opaque publish id.
